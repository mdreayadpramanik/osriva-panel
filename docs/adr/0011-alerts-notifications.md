# ADR-0011: Alerts, notifications and retention

Status: accepted (Phase 8a, 2026-11-03)

## Context

Phase 8 asks for metrics retention, alerts, SMTP and webhook notifications,
automation and audit retention. Alerts that fire on noise get ignored. Notification
secrets (webhook tokens, SMTP passwords) are credentials. Deleting audit entries must
itself be traceable.

## Decision

* **Evaluation in the panel.** The `monitor` service runs every 30 s and evaluates rules
  against stored samples and server state. The agents stay simple and cannot suppress
  their own alerts.
* **Rules:**

  | Metric | Fires when |
  |--------|------------|
  | `cpu`, `memory`, `load` | the average over the window is above the threshold |
  | `disk` | the fullest disk stayed above the threshold for the whole window (minimum over the window) |
  | `offline` | no report for longer than the threshold in minutes |
  | `backup` | the newest backup failed or expired |

  * A window counts only when samples cover at least 60 % of it, which avoids firing on
    a spike right after an agent starts. The query reaches 45 s further back to allow
    for the upload delay.
  * Missing data leaves the state unchanged; it never resolves or fires an alert.
  * The rule state is stored per rule and server. Only transitions create events
    (firing, resolved), so nothing repeats every cycle.
* **Channels:**
  * **Webhook:** a JSON POST signed with
    `X-Osriva-Signature: sha256=HMAC-SHA256(secret, timestamp "." body)` and
    `X-Osriva-Timestamp`. The 256-bit secret is generated by the panel and shown once.
    Redirects are not followed (they could carry the signed payload elsewhere), with a
    10 s timeout.
  * **E-mail:** SMTP with STARTTLS (required when chosen), implicit TLS, or none for
    local relays. PLAIN authentication is refused on an unencrypted connection by Go's
    `net/smtp`. CR/LF are stripped from the subject; rule and channel names cannot
    contain them.
  * Secrets are AES-256-GCM encrypted and bound to the channel ID.
  * Webhook URLs often embed tokens, so the audit log records only the host. Readers
    without `alerts.write` see the path and SMTP user name masked.
* **New permissions:** `alerts.read` (owner, admin, auditor) and `alerts.write` (owner,
  admin).
* **Metrics retention:** raw samples are kept 24 h. Hourly rollups (CPU average and
  maximum, memory, load, network, and the highest disk use) are written for completed
  hours, catching up 23 hours after downtime, and kept 90 days. Windows longer than 24 h
  are served from them.
* **Audit retention:**
  * A setting from 30 to 3650 days (default 365), changed by `settings.write` with
    re-authentication.
  * It is applied hourly and at start-up; each cleanup writes an `audit.pruned` entry
    with the count.
  * Shortening the retention deletes history, so the dashboard asks for confirmation.

## Limits

* Notifications are sent synchronously from the evaluation loop, without retries or a
  queue (Phase 9 brings Redis-backed queues).
* No silences, maintenance windows or escalation.
* **Automation** (scheduled actions, auto-remediation) is not part of 8a.
* Webhook targets are entered by trusted users (`alerts.write`). The panel can reach
  internal addresses, which is intended for self-hosted receivers.
